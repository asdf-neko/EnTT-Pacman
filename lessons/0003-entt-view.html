第3课：EnTT View — 批量查询实体

EnTT-Pacman 课程 · 第一部分：地基

View 是什么？

前两课学完了单个实体的 CRUD。但系统的真正威力在于批量操作——「把所有正在移动的东西往前挪一格」、「给所有追逐模式下的幽灵计算目标」。

View（视图）就是 EnTT 的批量查询机制。它回答一个问题：

「给我所有同时拥有组件 A、B、C... 的实体」

基本用法：

auto view = reg.view<Position, ActualDir>();     // 创建查询
for (const entt::entity e : view) {               // 遍历结果
  view.get<Position>(e).p += toPos(view.get<ActualDir>(e).d);
}

每行代码都在说什么？把它翻译成人话：

代码人话
reg.view<Position, ActualDir>()「筛选出所有同时有 Position 和 ActualDir 的实体」
for (auto e : view)「逐个处理筛选出来的实体」
view.get<Position>(e)「拿到这个实体的 Position 组件」

View 的核心规则

规则一：列出的组件越多，筛选越精确。
view<Position>() → 所有有位置的实体（玩家+幽灵+任何会动的东西）
view<Position, Player>() → 只有玩家
view<Position, Player, ChaseMode>() → （不合理的查询——玩家没有 ChaseMode，返回空）
规则二：view 是惰性查询。
它不复制数据，只是建立了一个「遍历路径」。在迭代过程中，如果组件被修改/移除/添加了，view 能感知到。

项目中所有 View 查询一览

打开项目，数一数每个系统用了什么样的 view——你会发现 view 的组件组合直接定义了系统的职责范围：

系统View 查询翻译
movement() view<Position, ActualDir> 「所有能移动的东西」
wallCollide() view<Position, ActualDir, DesiredDir> 「所有能改变方向的东西」
playerInput() view<Player, DesiredDir> 「只有玩家」
pursueTarget() view<Target, Position, ActualDir, DesiredDir> 「所有有追踪目标的东西」（幽灵）
setBlinkyChaseTarget() view<Target, ChaseMode, BlinkyChaseTarget> 「追逐模式下的 Blinky」
setClydeChaseTarget() view<Target, Position, ChaseMode, ClydeChaseTarget, HomePosition> 「追逐模式下的 Clyde」（需要5个组件！）
setScatterTarget() view<Target, ScatterMode, HomePosition> 「散射模式下的幽灵」
setScaredTarget() view<Target, Position, ScaredMode, ActualDir> 「恐惧模式下的幽灵」
setEatenTarget() view<Target, EatenMode, HomePosition> 「被吃掉、正在回家的幽灵」
ghostScared() view<Ghost>() 「所有幽灵（单组件查询）」
ghostChase() view<Ghost, ScatterMode>() 「散射模式下的幽灵→切换为追逐」
一个重要的设计洞察：你可以直接从 view 的组件列表推断出系统的职责。当你写一个新系统时，第一件事就是问自己：「我要操作拥有哪些组件的实体？」——答案就是你的 view 签名。

为什么用 view.get() 而不是 reg.get()？

两种写法都能拿到组件引用，但有区别：

// 写法 A：view.get（推荐）
auto view = reg.view<Position, ActualDir>();
for (auto e : view) {
  view.get<Position>(e);    // ✅ view 已经知道实体有这个组件，直接返回引用
}

// 写法 B：reg.get（可以但不推荐）
for (auto e : view) {
  reg.get<Position>(e);    // ⚠️ reg 需要重新查找组件存储，稍慢
}

在 view 循环内，始终用 view.get<T>(e)。 在 view 循环外（比如你需要访问其他实体的组件时），用 reg.get<T>(otherEntity)。

进阶模式：同一系统中使用多个 View

有些系统需要比较两类不同的实体——比如碰撞检测：

// src/sys/player_ghost_collide.cpp（简化）
GhostCollision playerGhostCollide(entt::registry ®) {
  const auto players = reg.view<Player, Position, ActualDir>();   // 玩家组
  const auto ghosts  = reg.view<Ghost, Position, ActualDir>();    // 幽灵组

  for (const entt::entity p : players) {       // 外循环：每个玩家
    const Pos playerPos = players.get<Position>(p).p;
    for (const entt::entity g : ghosts) {      // 内循环：每个幽灵
      const Pos ghostPos = ghosts.get<Position>(g).p;
      if (collide(playerPos, ghostPos, ...)) {
        // 碰撞发生！
      }
    }
  }
}

这里用了两个独立的 view，分别迭代玩家和幽灵，然后做笛卡尔积比较。这是处理「A 类实体 vs B 类实体」交互的标准模式。

迭代中修改组件：安全吗？

在 view 循环中增删当前实体的组件是安全的（EnTT 内部处理了迭代器失效）：

// src/sys/change_ghost_mode.cpp
for (const entt::entity e : reg.view<Ghost, ScatterMode>()) {
  reg.remove<ScatterMode>(e);    // ✅ 安全：移除当前实体的组件
  reg.emplace<ChaseMode>(e);     // ✅ 安全：添加新组件
}
但要注意：如果你在循环中创建或销毁其他实体，可能触发存储扩容导致迭代器失效。对当前实体本身操作是 OK 的。

为什么 View 这么快？

理解这一点不是必须的，但它能帮你建立正确的直觉：

  1. 同类型组件连续存储——所有 Position 组件紧挨着放在内存里，CPU 缓存友好。
  2. View 从最小的集合开始迭代——比如 view<Ghost, ScaredMode>()，EnTT 会先找 Ghost 和 ScaredMode 中实体更少的那一组，从它开始遍历，减少检查次数。
  3. 没有虚函数、没有指针跳转——所有操作都是直接内存访问。

测验答案
  1. 处于 ScatterMode（散射模式）下的幽灵。因为同时拥有 Target、ScatterMode、HomePosition 的实体只能是幽灵——玩家没有这些组件。
  2. view<Ghost, ScaredMode, ActualDir>()（或至少 view<Ghost, ScaredMode>()）。你需要筛选出同时是幽灵且处于恐惧模式的实体，然后修改它们的移动逻辑。如果需要在系统中修改方向，还要加上 ActualDir。
  3. view.get<T>(e) 更快——因为 view 在创建时已经确定了组件存储的位置，不需要重新查找。reg.get<T>(e) 每次调用都需要在 registry 中查找。在 view 循环中始终用前者。
