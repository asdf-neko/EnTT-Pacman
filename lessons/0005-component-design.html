设计模式一：Tag Component — 用空结构体标记状态

7 个组件是空的。它们不存数据，只做一件事：让 view 能筛选。

// 身份标签
struct Player {};     // 只需 view<Player>() 就能找到玩家
struct Ghost {};      // 只需 view<Ghost>() 就能找到所有幽灵

// 模式标签 — 幽灵同时只能处于一种模式
struct ChaseMode {};
struct ScatterMode {};
struct EatenMode {};

// "门票"标签 — 控制鬼屋进出权限
struct EnterHouse {};
struct LeaveHouse {};

这些空组件有什么共同点？它们回答的都是「是什么」或「处于什么状态」——这正是 ECS 替代 OOP 继承的方式。不再用 class Ghost : public ChaseBehaviour，而是给实体挂 ChaseMode 标签。

为什么是多个 struct 而不是一个 enum？
如果用 enum GhostMode { Chase, Scatter, Scared, Eaten }，view 查询会变成：
view<GhostMode>() → 拿到所有幽灵，然后手动 if (mode == Chase)。
用独立 struct，EnTT 在查询阶段就完成了筛选：
view<ChaseMode>() → 直接拿到追逐中的幽灵，零条件判断。

设计模式二：Data Component — 数据在最外层

数据组件都遵循一个原则：要用的数据直接放在 struct 顶层，不要嵌套。

// ✅ 好设计 — 数据在外层
struct Position { Pos p; };
struct DesiredDir { Dir d; };
struct Target { Pos p; };

// ❌ 避免 — 不需要多余的封装层
struct Position {
  Pos getPos() const { return p; }   // ECS 组件不需要方法！
  void setPos(Pos newP) { p = newP; }
private:
  Pos p;   // 不需要 private！
};
ECS 组件的第一原则：组件是纯数据，没有方法，没有 private。系统直接读组件字段——最快的路径。封装和 getter/setter 在这里是多余的噪音。

设计模式三：实体引用 — 用 entity 作为组件字段

这是 EnTT-Pacman 中最优雅的设计之一。每种幽灵的追逐目标组件存的是实体 ID，而不是位置：

// Blinky 追逐玩家 — 存玩家的实体 ID
struct BlinkyChaseTarget {
  entt::entity player;     // ← 存的是 entity，不是 Position！
};

// Inky 需要两个信息：玩家位置 + Blinky 位置
struct InkyChaseTarget {
  entt::entity player;     // 玩家
  entt::entity blinky;     // Blinky
};

使用时通过实体 ID 取对方的位置：

// src/sys/set_target.cpp — Blinky 的追逐目标就是玩家的位置
auto view = reg.view<Target, ChaseMode, BlinkyChaseTarget>();
for (auto e : view) {
  const entt::entity player = view.get<BlinkyChaseTarget>(e).player;
  view.get<Target>(e).p = reg.get<Position>(player).p;   // 解引用！
}
原作者在注释中说：「这就是 ECS 的美妙之处。Blinky 不一定非要追玩家——BlinkyChaseTarget 只存一个有 Position 的实体 ID。Blinky 可以追 任何 有位置的东西。我们甚至可以让他追 Inky！」

设计模式四：「门票」模式 — EnterHouse / LeaveHouse

幽灵进出鬼屋是一个有趣的设计问题：鬼屋有门，门一次只能过一个方向的幽灵。作者的解决方案是门票组件：

// 幽灵有了 EnterHouse 门票 → 可以通过门进入屋子
struct EnterHouse {};

// 幽灵有了 LeaveHouse 门票 → 可以通过门离开屋子
struct LeaveHouse {};

门票何时发放？

// 创建时：幽灵出生在房子里，默认带 LeaveHouse 门票
makeGhost(reg, home, scatter) {
  reg.emplace<LeaveHouse>(e);    // ← 出生就有出去的门票
}

// 被吃时：幽灵获得 EnterHouse 门票
void ghostEaten(entt::registry ®, entt::entity ghost) {
  reg.emplace<EnterHouse>(ghost);   // ← 被吃后获得回家的门票
}

// 进门后：门票被收回
// （enterHouse 和 leaveHouse 系统在实体通过门后 remove 相应的门票）

设计模式五：ScaredMode — 标签和数据的混合体

ScaredMode 是唯一一个既有标签作用又有数据的组件：

struct ScaredMode {
  int timer = ghostScaredTime;   // 恐惧倒计时（40 ticks）
};

为什么不让它和空标签统一？因为恐惧模式需要一个计时器。如果拆成两个组件：

// ❌ 不好的设计
struct ScaredMode {};
struct ScaredTimer { int timer; };

// 系统需要同时查两个组件
reg.view<ScaredMode, ScaredTimer>();  // 啰嗦

数据紧跟着状态走，合并成一个组件更简洁。

从表中能看出什么？
  • 所有实体共享 Position + DesiredDir + ActualDir —— 因为都需要移动
  • 幽灵比玩家多 Target + HomePosition —— 因为它们需要 AI 导航
  • 玩家独有 PlayerSprite，幽灵独有 GhostSprite —— 渲染系统用不同的逻辑
  • 每种幽灵有自己专属的 ChaseTarget 类型 —— 因为每种幽灵的追逐算法不同

为什么每种幽灵有独立的 ChaseTarget 组件？

这是作者做的一个明确的设计选择。来看看替代方案：

// 替代方案 A：统一组件 + 枚举
struct ChaseTarget {
  GhostType type;        // Blinky / Pinky / Inky / Clyde
  entt::entity player;
  entt::entity blinky;   // 只有 Inky 用，其他幽灵浪费内存
};

// 替代方案 B（本项目）：每种幽灵独立组件
struct BlinkyChaseTarget { entt::entity player; };
struct PinkyChaseTarget  { entt::entity player; };
struct InkyChaseTarget   { entt::entity player, blinky; };
struct ClydeChaseTarget  { entt::entity player; };

方案 B 的优势：每个幽灵只存它真正需要的数据。Inky 需要额外存 blinky 的引用，其他幽灵不需要。而且系统可以直接用 view<ChaseMode, BlinkyChaseTarget>() 精确筛选——不需要额外的 if/switch。

取舍：方案 B 的代价是每个幽灵需要各自独立的 setTarget 系统（setBlinkyChaseTarget、setPinkyChaseTarget...），代码重复度更高。如果幽灵种类很多，方案 A 可能更合适。选择取决于具体场景。

设计清单：写组件前问自己

  1. 这个数据属于单个实体，还是全局共享？ → 前者用组件，后者放 Game 类
  2. 只是标记状态，还是要存数据？ → 前者用空 struct，后者加字段
  3. 需要和其他组件一起查询吗？ → 想想你需要的 view 签名长什么样
  4. 每个实体都会用这个数据吗？ → 如果是，合并进已有组件；如果只少数用，新建组件

测验答案
  1. 因为 EnTT 的 view 可以直接按类型筛选。用 enum 的话 view<GhostMode>() 拿到所有幽灵，还要手动 if/switch。用独立 struct，view<ChaseMode>() 在查询阶段就完成了筛选。
  2. 因为 Inky 的追逐算法需要同时知道玩家位置和Blinky 位置（Inky 的目标 = Blinky 的位置 + (玩家前方两格 - Blinky 位置) × 2）。其他三种幽灵只需要玩家位置。
  3. 需要新增一个 Speed 组件（存储速度倍率），在 movement 系统中读取它，在吃能量豆时给 Player 挂上（带计时器），超时后自动移除。或者在已有的组件中增加字段——但这会让组件职责变模糊，独立组件更好。
